- Monthly client reports are built by the `monthly-report-data` edge function (super-admin JWT or a property's public_report_token) and rendered client-side as fixed Letter `.rd-page` blocks exported page-by-page to PDF; why: one document serves both the admin tab and the shareable client link.
- Marketing Ops data lives in the non-exposed `mops` schema and is reachable only through `mops-api`/`mops-ai` via the shared guard (JWT identity + explicit single grant, never role); the browser only calls `mops_my_access` for menu/route display. Why: least-privilege isolation from Bob, reports and other staff.
- Marketing Ops SOPs are versioned master templates (`mops.sop_*`); clients are pinned to a version and statuses are keyed by node `stable_key`, served via `public.mops_sop_api` (same grant check as `mops_api`; the guard routes `sop_*` ops to it). Why: template edits never rewrite client history, and the private boundary stays single-entry.
- SOP completion, readiness and blockers are computed only in `src/lib/mops/readiness.ts`, and UI pieces in `src/components/ops/` are presentational and styled via `--ops-*` tokens. Why: the visual layer can be redesigned without touching logic.
