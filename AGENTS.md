- Monthly client reports are built by the `monthly-report-data` edge function (super-admin JWT or a property's public_report_token) and rendered client-side as fixed Letter `.rd-page` blocks exported page-by-page to PDF; why: one document serves both the admin tab and the shareable client link.
- Marketing Ops data lives in the non-exposed `mops` schema and is reachable only through `mops-api`/`mops-ai` via the shared guard (JWT identity + explicit single grant, never role); the browser only calls `mops_my_access` for menu/route display. Why: least-privilege isolation from Bob, reports and other staff.
- Marketing Ops SOPs are versioned master templates (`mops.sop_*`); clients are pinned to a version and statuses are keyed by node `stable_key`, served via `public.mops_sop_api` (same grant check as `mops_api`; the guard routes `sop_*` ops to it). Why: template edits never rewrite client history, and the private boundary stays single-entry.
- SOP completion, readiness and blockers are computed only in `src/lib/mops/readiness.ts`, and UI pieces in `src/components/ops/` are presentational and styled via `--ops-*` tokens. Why: the visual layer can be redesigned without touching logic.
- Google Ads campaign identity is the campaign ID, never its name: `sync-google-ads` stores `campaign_id` and calls `reconcile_campaign_renames` each run to fold old-name history into the current name (logged in `campaign_rename_log`); why: renames otherwise double-count spend and break label scoping.
- GHL→CTM Form Sync lives in `mops-form-sync` (guarded user path + cron-secret scheduled path via `mops_formsync_internal`), ledger in `mops.form_sync_*`, logic in injectable `engine.ts` with scenario tests; CTM posting requires the location's `delivery_enabled` AND `FORM_SYNC_LIVE`, rows are marked in-flight before posting and verified by submission ID/receipt before any retry, and pre-activation or unmapped-form submissions stay held until individually approved. Why: every legitimate lead reaches CTM exactly once without duplicating WordPress deliveries.
- Lead Reconciliation extends `mops-form-sync`: per-location mode (off/monitor/live) and manual_hold live in `mops.form_sync_config`; daily read-only preflight (`recon.ts`) may only move off↔monitor, never to live and never past a manual hold; live is an explicit administrator action; call discrepancies are computed from synced tables and never write to CTM/GHL. Why: automatic onboarding without risking duplicate CTM activity.
- Asana development log: change entries live in private `mops.dev_log_*` and sync to the "Dashboard Management" Asana project via `mops-asana-sync` (guarded user path + cron-secret hourly path); the agent records each material change at request time with `devlog_upsert` (stable change_id, original reasoning included — never invented later). Why: Asana is the authoritative decision log; Lovable exposes no request history after the fact.
